# Deploying Sarthi IAS Video Studio

Status: the configuration in this repository has been built and tested locally. Nothing has been deployed. Every step below needs the owner's accounts, and none of them has been carried out yet.

```
Browser ──► Vercel (web/dist, rewrites /api/* to Render)
                │
                ▼
           Render web service  sarthi-studio-api      (api.Dockerfile, uvicorn)
                │        │
                │        └──────► S3-compatible bucket (private; signed URLs only)
                ▼                        ▲
           Render PostgreSQL ◄──── Render background worker  sarthi-studio-worker
           (records + job queue)        (worker.Dockerfile: engine, HyperFrames, models)
```

## 1. What the owner provides

| Item | Used for | Where it goes |
| --- | --- | --- |
| A Git repository (GitHub, GitLab, or Bitbucket) | Render and Vercel build from it | Owner's account |
| Render account, paid plans | API web service, worker, PostgreSQL | Render dashboard |
| Vercel account | The website | Vercel dashboard |
| Cloudflare R2 or AWS S3 bucket and an access key scoped to it | All uploads, work files, and videos | Render env vars |
| ElevenLabs API key | Transcription (worker only) | Render env var on the worker |
| Gemini API key (optional) | Only if Gemini clip analysis is wanted | Render env var on the worker |
| Email address and name of the first studio account | Sign-in | Typed into `app.cli create-user` |

Never paste a key into source code, `render.yaml`, `vercel.json`, a `VITE_` variable, or a chat.

## 2. Repository

The repository root is the project folder that holds `LOGO/`, `OUTRO/`, `reference_dataset/`, and `saarthi_video_engine/`, because the images copy the logo, outro, and `shorts_dataset.json` from there. The root `.gitignore` admits only those, the engine code, and the licensed music file with its record. Raw lectures (`DR_SHIVIN_RAW/`), `reference_inputs/`, historical `outputs/`, `data/`, `tools/`, virtualenvs, and every `.env` stay out.

From the project folder: `git init`, `git add .`, check `git status` lists no video other than `OUTRO/` and the licensed `.ogg`, commit, and push to the new remote.

## 3. Object storage

1. Create a private bucket, for example `sarthi-studio`. Do not enable public access or a public domain.
2. Create an access key limited to that bucket with object read and write.
3. Add a CORS rule so the browser can upload straight to the bucket:

```json
[
  {
    "AllowedOrigins": ["https://<your-vercel-domain>"],
    "AllowedMethods": ["PUT", "GET", "HEAD"],
    "AllowedHeaders": ["content-type"],
    "ExposeHeaders": ["ETag"],
    "MaxAgeSeconds": 3600
  }
]
```

For R2 the endpoint is `https://<account-id>.r2.cloudflarestorage.com` and the region is `auto`. For AWS S3 leave the endpoint empty and set the bucket's region.

## 4. Render

1. Dashboard → New → Blueprint → choose the repository. Render reads `render.yaml` from the repository root.
2. Review the plans before applying: `basic-256mb` PostgreSQL, `starter` API, `standard` worker (2 GB RAM; CLIP and headless Chrome need it), region `singapore`. Change them in `render.yaml` if needed.
3. Enter the values marked `sync: false`:
   - shared group `sarthi-studio-shared`: `OBJECT_STORAGE_ENDPOINT`, `OBJECT_STORAGE_BUCKET`, `OBJECT_STORAGE_ACCESS_KEY`, `OBJECT_STORAGE_SECRET_KEY`;
   - API: `STUDIO_CORS_ORIGINS` = the Vercel origin, for example `https://<project>.vercel.app`;
   - worker: `ELEVENLABS_API_KEY`, and `GEMINI_API_KEY` only if wanted (leave it empty otherwise).
   `STUDIO_SESSION_SECRET` is generated by Render and shared by both services. `DATABASE_URL` comes from the database.
4. Apply. The API image builds from `saarthi_video_engine/deploy/api.Dockerfile`; before each deploy Render runs `python -m app.cli migrate`. The worker image (`worker.Dockerfile`) downloads the two models and the pinned HyperFrames Chrome while it builds, so it takes longer.
5. Create the first account from the API service's Shell tab:

```
python -m app.cli create-user --email <owner-chosen address> --name "<name>"
```

   The password is typed at the prompt (12 characters or more) and is not echoed or logged. Other commands: `set-password --email`, `disable-user --email`, `enable-user --email`.

| Service | Build | Start | Health |
| --- | --- | --- | --- |
| API | `deploy/api.Dockerfile`, context = repository root | `uvicorn app.main:app --host 0.0.0.0 --port $PORT --proxy-headers` | `/api/live` (Render's check); `/api/ready` for monitoring |
| Worker | `deploy/worker.Dockerfile`, context = repository root | `python -m app.worker` | Heartbeat row in `workers`; `/api/ready` reports it |
| Migrations | in the API image | `python -m app.cli migrate` (pre-deploy; exits 1 unless every table exists at the head revision) | `python -m app.cli check-schema` prints the revision; head is `0002_repair_missing_tables` |

Render's health check uses `/api/live` on purpose: `/api/ready` returns 503 while the worker is down or the schema is behind the code, and that should not stop the API from serving sign-in and review.

Only the API migrates. The worker does not: on start it waits up to `STUDIO_SCHEMA_WAIT_SECONDS` (600 by default) for the database to reach the head revision, logging `waiting for database migrations` with the database host and name, then registers and polls. If the schema never arrives it exits with a message naming the database, which usually means the API and worker have different `DATABASE_URL` values.

### Deploying the intelligent-editing upgrade

No new environment variables are required and no migration is added. Both images now also contain `assets/music_library/`. Because `render.yaml` sets `autoDeploy: false`, deploy by hand after the push: first `sarthi-studio-api` (its pre-deploy `migrate` should report `0002_repair_missing_tables`), then `sarthi-studio-worker`. Vercel deploys the website from the push on its own.

Optional: to let the editing assistant fall back to Gemini for instructions its built-in rules do not understand, add `GEMINI_API_KEY` to the **API** service as well (it is currently only on the worker). Without it the assistant still works with its rules and asks a question when unsure. `STUDIO_KEEP_SCRATCH=1` keeps a worker's scratch folder for debugging; do not set it in production.

## 5. Vercel

1. New Project → import the same repository. Root Directory: `saarthi_video_engine/web`. Framework: Vite. `vercel.json` sets `npm ci`, `npm run build`, and `dist`.
2. Environment: leave `VITE_API_BASE_URL` empty. `vercel.json` rewrites `/api/*` to `https://sarthi-studio-api.onrender.com`. If Render gives the API a different hostname, edit that one line and redeploy.
3. Deploy, then put the Vercel origin in the API's `STUDIO_CORS_ORIGINS` and in the bucket CORS rule.

Calling the API origin directly (setting `VITE_API_BASE_URL`) also works, but the cookie then crosses sites: set `STUDIO_COOKIE_SAMESITE=none` on the API. The rewrite is simpler and keeps the cookie first-party.

## 6. Verification before calling it deployed

1. `https://<vercel-domain>/api/live` → `{"status": "alive"}`; `/api/ready` → 200 with `database`, `object_storage`, `queue`, `worker`, `ffmpeg` all `ok`.
2. Sign in with the account from step 4.5; refresh the page and confirm you are still signed in; sign out.
3. Staging smoke, one short lesson each:
   - AI Auto-Edit (Mode A): upload, process, review the plan and its Commons licences, render, preview, download.
   - Edit with My B-Roll (Mode B): upload the lesson and one described clip, process, check the clip analysis provider, change the title, render, preview, download.
   - In the bucket, `renders/<session>/<render>/` holds `composition/lint.txt` and `composition/render.txt` written by HyperFrames 0.8.186, and `final.mp4` is not readable without a signed URL.
4. Compare the staging Mode B video with a local render of the same plan. On Linux the title card's Arial is drawn with Liberation Sans, which has the same metrics; approve production only if the owner accepts the look.

Only after these pass should the deployment be described as live.

## 7. Operations

- Logs are JSON lines with `request_id`, `user_id`, `session_id`, `job_id`, `render_id`, `plan_version_id`, `stage`, `duration_seconds`, and `failure_category`. Keys, cookies, passwords, and signed-URL signatures are redacted.
- One worker runs one job at a time. Add worker instances for more parallel jobs; the queue hands each job to one worker.
- Rotating `STUDIO_SESSION_SECRET` signs everyone out. Rotate storage keys in the bucket provider, then update both services.
- Backups: Render PostgreSQL backups follow the plan; turn on bucket versioning if deleted objects must be recoverable.
- Rollback: Render can redeploy an earlier image. The single migration only adds tables; a downgrade drops them and their data.
- Older local sessions are not uploaded automatically. To bring some in, run `python -m app.tools.import_local --source <folder>` (a dry run), then add `--apply --owner-email <address>`, with the production `DATABASE_URL` and `OBJECT_STORAGE_*` in the environment.

## 8. Local rehearsal

`deploy/smoke_local.py` starts an S3 stand-in, the API with sign-in and the queue runner, and a separate worker on one machine, then drives one lesson through the browser's HTTP calls with the real renderer. It blanks the ElevenLabs and Gemini keys and seeds the transcript cache, so it cannot spend credits. It is a rehearsal, not a deployment.
